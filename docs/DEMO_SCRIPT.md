# CivicSync demo — approximately 3–4 minutes

Only record this after the merged system passes live acceptance. Use a staging database with **clearly labelled test records entered through the actual forms**. Never present test works as real municipal projects. Do not preload unsaved arrays or edit dashboard numbers for a video.

## Before recording

Have approved officials in two departments and a citizen in separate real browser sessions. Make sure both official accounts were approved through Person 2’s backend process. Prepare a genuine shared road-segment identifier for the test location, valid nearby map coordinates, two intrusive work types and overlapping dates. Start from a known staging state; record IDs of any reused records rather than repeatedly creating duplicates. Check the deployed route and available tile connection.

## 0:00–0:35 — The citizen view

Open the actual deployed dashboard. Explain: “CivicSync puts registered public works and their saved updates in one place. These are explicitly labelled staging records.” Search for the first project, apply a department/status filter and open its map/details. Show its saved dates, department and timeline. Refresh the browser once so persistence is visible.

## 0:35–1:25 — Register overlapping work

As the first approved official, save a mapped water/excavation project. As the second, save telecom or another intrusive work at the same test segment or within 30 metres, with overlapping dates. Show that the forms save actual database records. Open Dig-Once review: a persisted alert gives the specific pair, date overlap and location/work-type evidence. Explain that the database trigger—not only a browser button—created it, and that it identifies a potential coordination issue rather than proving an engineering hazard.

## 1:25–2:15 — Record a decision

As an involved official, open the decision dialog. Record a meaningful public coordination note; do not write “fixed” unless an actual schedule/update supports that statement. Save, reload and open history. Show one canonical pair and the retained decision. A “resolved” decision records coordination; it does not secretly alter project dates.

## 2:15–3:00 — Publish an actual change

Use the project’s update form to revise an end date/status with an explanatory note. Show the project and citizen-visible timeline reflecting the same saved change. When the changed dates remove overlap, show the conflict clearing; when material overlap remains, show the alert reopening for fresh review. Describe what actually happened in this chosen example rather than promising a predetermined outcome.

## 3:00–3:40 — Citizen reporting and persistence

In the citizen session, submit a concrete non-emergency issue for a selected project. Open My Reports and refresh to show the saved report. In an authorized staff session, open Department reports, record a review status and response, then return to the citizen session and refresh to show the persisted change. End by showing the deployed URL and repository commit used for the test.

## If a dependency fails

Show the actual error and state the missing dependency. Do not substitute a screenshot, synthetic response or local array while saying the backend is working. A recording can be postponed; a fabricated persistence claim cannot be justified.
